# E — Figma drift handoff: deterministic CI, local implementation

Common rules: [README.md](./README.md). Source: assessment §5, action E (G9).
Depends on **A1** and **B**; can run with **A2**.

## Goal

Turn the Figma drift into a **deterministic pull request** that carries the delta
and everything needed to implement it, and hand that pull request to the person,
who implements it **locally with their own coding agent**. CI does not run a
coding agent.

- CI: fetch the live file read-only, compare it with the committed catalogue,
  refresh the inventory, queue the delta, open one review pull request.
- Person: start a coding agent in a worktree on the drift branch, follow the
  `figma-to-code` skill, run the checks and the comparisons, record the
  decisions.
- Review: the merge of the drift pull request is the review record.

## What “agent” means here

The **coding agent** is the assistant the person runs locally in the worktree
(the same `figma-to-code` and `pagopa-ui-standards` skills a normal session
uses). It is not a component of the CI pipeline and it has no credential in the
repository.

A CI **agent job** would be the opposite design: an autonomous agent CLI
executed inside GitHub Actions, one job per delta node, with a model
credential, a cost and a time budget, permission to commit and to open pull
requests, and a termination policy. This flow does **not** use that design. It
is listed under “Out of scope” so the choice is explicit.

## Non-goals

- Running a coding agent in CI, with or without a matrix of jobs.
- Implementing the delta automatically.
- Writing to Figma, with any tool.
- Changing the comparison tools, the components or the instructions.

## Scope and files

The flow owns:

- `.github/workflows/figma-drift.yml` — verify it and extend it with the delta
  artifact, the run metadata and the artifact upload; the drift semantics stay.
- `.github/scripts/figma-drift/*` — only if a deterministic step is needed
  (for example a branch-guard check, or a handoff file builder). No model call,
  no network call beyond the Figma REST read.
- `docs/plans/e-ci-handoff.md` — the local handoff procedure: worktree, token,
  prompt, checks, delivery rules.
- `docs/plans/e-ci-secrets.md` — the secrets and permissions document.

The flow does not touch the comparison tools (`packages/ui-cli/src/parity`,
`packages/ui-cli/src/figma/sync.ts`), the components, or the instructions
(`AGENTS.md`, `CONTRIBUTING.md`, `README.md`, `.agents/**`). A change there is a
handoff.

## Decisions

- **Deterministic CI.** The drift job does only fetch, compare, refresh, open the
  pull request. No model, no agent, no per-node matrix.
- **One pull request for the whole delta.** The person implements in a single
  worktree; the branch is the review unit. Per-node pull requests are not part of
  this flow.
- **The person's environment is the implementation environment.** The local
  agent uses the person's `.figma` snapshot, their `FIGMA_TOKEN` and their
  browser, as every local session does.
- **Read-only Figma, in both places.** CI reads through REST; the local session
  reads through REST or the MCP read tools. No write tool.
- **The merge is the record.** `implemented` follows an inspected render, not a
  green suite or a thumbnail.
- **The completion criteria are objective**: `figma:check`, `foundation:check`,
  `layers:check`, `figma:parity:check` and the targeted tests. Chromatic stays
  opt-in (A1).

## Procedure

### 1. Verify the deterministic drift path

The drift job must work end to end with the read-only token:

1. the read-only REST read succeeds (`FIGMA_TOKEN` present, no `.env`);
2. the comparison reports the delta, or “no drift” with no pull request;
3. the refresh writes `inventory.json`, `registry.json` and
   `evidence-exceptions.json`, and queues the delta nodes as `pending`
   (`mocked` and `excluded` keep their status);
4. the review pull request opens on `figma-drift/<date>` with the generated
   body;
5. the dependencies install with the registry authentication, and the job does
   not log the token.

Any failure here is fixed inside the workflow, not in the tooling.

### 2. Add the deterministic artifacts

Extend `figma-drift.yml` so the run leaves, next to the pull request:

- `delta.json` from the `--plan` output: `added`, `changed`, `affected`,
  `renamed`, `moved`, `baseline`, `implementationOrder`, the device summary and
  the coverage summary;
- `run.json` with the drift branch and the pull request number;
- the generated PR body.

The delta for the implementation is `added ∪ changed ∪ affected`, minus
`mocked` and `excluded`; `baseline` nodes are reported separately because they
have no design fingerprint and cannot be verified. Upload the artifacts with a
short retention; do not upload the whole `.figma/` directory.

### 3. Guard the branch

The job force-pushes `figma-drift/<date>`; a re-run on the same day must not
destroy work a person has already done on that branch.

Before pushing, the job checks whether the remote branch exists and its head is
the bot’s last commit. If it has moved, the job fails with a message and opens
nothing; the person decides whether to refresh or to continue on their branch.
A no-drift re-run opens nothing.

### 4. Document the handoff

Add `docs/plans/e-ci-handoff.md` with the exact local procedure:

```sh
git worktree add ../pagopa-ui-drift -b drift/figma-<date> origin/figma-drift/<date>
cd ../pagopa-ui-drift
pnpm install
ln -s ../pagopa-ui/.figma .figma   # the pinned snapshot, when the person keeps one
export FIGMA_TOKEN=...
# start the coding agent in this worktree
```

The procedure states:

- which skill to load (`figma-to-code`, delta use case) and which references;
- the delta and the order of the work, taken from the pull request body or from
  `delta.json`;
- the forbidden actions: Figma writes, changes to the comparison tools, to the
  instructions, or to the public API without a decision;
- the checks to run and the expected result
  (`pnpm nx run pagopa-ui:figma:check`, `foundation:check`, `layers:check`,
  `figma:parity:check --node <id>` and `--devices` for a device set, the targeted
  tests, the full chain of `CONTRIBUTING.md`);
- the delivery: the local session commits on the drift branch; the person pushes
  and merges (common rule 9 stays true: the session does not push).

### 5. Secrets and permissions

CI needs only what the deterministic path uses:

| Secret                    | Scope                                       | Used by           | Failure mode                                      |
| ------------------------- | ------------------------------------------- | ----------------- | ------------------------------------------------- |
| `FIGMA_TOKEN`             | `file_content:read`, `library_content:read` | drift job         | the job fails at the preflight                    |
| `DRIFT_PR_TOKEN`          | contents + pull requests                    | drift job         | the pull request exists but its checks stay empty |
| `NODE_AUTH_TOKEN`         | `packages: read`                            | drift job install | install `401`                                     |
| `CHROMATIC_PROJECT_TOKEN` | Chromatic project                           | A1, opt-in        | the opt-in baseline is skipped                    |

The workflow keeps minimal permissions (`contents: write`, `pull-requests:
write`, `packages: read`), never prints a token and never writes to Figma. No
agent credential exists, because no agent runs in CI.

Add `docs/plans/e-ci-secrets.md` with the table above, how to create each secret
and rotate it, and the statement that the agent does not insert them and never
reads `.env`.

### 6. Metrics

Record per drift run:

- `figma_change_at`: the Figma version timestamp of the drift snapshot, or the
  run start when the version carries no timestamp;
- `handoff_pr_at`: the creation time of the drift pull request;
- `merged_at`: the merge time of the drift pull request;
- the number of delta nodes queued;
- the number of handoffs that needed a manual refresh, a missing secret or a
  branch conflict.

The two reported metrics are `handoff_pr_at − figma_change_at` and
`merged_at − handoff_pr_at`. The percentage of drift pull requests completed
“without human intervention during implementation” is **not** a metric of this
flow: the person and their agent are the implementation.

## Acceptance

- **A deterministic run.** With `FIGMA_TOKEN` configured, a
  `workflow_dispatch` run reads the live file, reports the delta and opens
  `figma-drift/<date>` with the generated body; a second run with no drift opens
  nothing and leaves the catalogue untouched.
- **A synthetic drift.** On a test branch, a modified inventory makes the gate
  and the body report the node and queue it `pending`; the branch is not merged.
- **Artifacts.** The run uploads `delta.json`, `run.json` and the PR body; the
  body lists the delta, the devices, the links, the review decisions and the
  verify chain.
- **The guard.** A re-run over a branch that has moved fails with a clear
  message instead of force-pushing.
- **A local handoff trial.** The person follows `e-ci-handoff.md` on one queued
  node, starts the coding agent, and produces a branch with the checks and the
  parity case green; the trial is reported with the commands, the node and the
  result. This trial runs locally, not in CI.
- **The secrets document** is committed and no token appears in the run logs.
- **The full green chain** of `CONTRIBUTING.md` is green on the drift branch
  after the local implementation.
- No file outside the ownership above is touched; every outside-scope need is in
  the handoff list.

## To ask the person

1. Confirm the scope: the deterministic handoff PR, with the implementation
   local and the coding agent outside CI. If the “no person during
   implementation” goal of G9 must stay, this flow does not meet it and the
   CI-agent design is the alternative.
2. Insert `FIGMA_TOKEN` and `DRIFT_PR_TOKEN`, and where to document them.
3. Keep one drift pull request for the whole delta, or one per node (with the
   local agent working one node at a time).
4. Should the drift run also carry a snapshot artifact, or is the person’s local
   `.figma` snapshot the only source for the parity tools?
5. Keep the weekly schedule, or move to daily / manual dispatch to reduce
   `figma_change_at → handoff_pr_at`.
6. May this flow update `docs/plans/README.md` (the index row, the session
   kickoff, the common rules), or is that a separate change?

## Out of scope

- Running a coding agent in CI, in any form (single job, matrix, per node).
- An agent credential, a model budget or a per-node cost and time policy.
- The comparison tools and the parity source (A1).
- The components, the stories and the instructions (F0 and A2).
- Inserting the secrets or creating the environments.
- Auto-merging the drift pull request.

| Owner             | Item                                                                                                                                                                                          |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

## Risks

| Risk                                         | Impact                                     | Mitigation                                                                        |
| -------------------------------------------- | ------------------------------------------ | --------------------------------------------------------------------------------- |
| A missing `FIGMA_TOKEN` or `DRIFT_PR_TOKEN`  | no drift pull request, or an unchecked one | document both in the secrets file; verify with one `workflow_dispatch` run        |
| A same-day re-run over a branch in use       | lost local commits                         | the branch guard before the push                                                  |
| The drift body does not change with the flow | the handoff text stays generic             | handoff to A1 for the generator; the flow adds `delta.json`                       |
| The local agent follows a stale skill        | a wrong implementation                     | the person is the guard; the skill is the F0 handoff                              |
| A large delta                                | a long local session                       | `implementationOrder` in the body and in `delta.json`; the person splits the work |
| The snapshot is not available locally        | the parity tools do not run                | the handoff procedure exports it with `FIGMA_TOKEN`                               |

## Definition of done

- The acceptance criteria are verified, or the unverified ones are named with
  the missing prerequisite.
- The green chain of `CONTRIBUTING.md` is green.
- The secrets document is committed; no secret is in the logs or in the
  repository.
- CI never calls an agent and never writes to Figma.
- Every outside-scope need is in the handoff table.
- The final report states what was done, the commands and their outcome, the
  before/after numbers, what is missing and why, and the decisions that need the
  person.
